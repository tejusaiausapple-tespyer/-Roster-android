## 1. Tech stack & architecture

- **UI**: 100% SwiftUI (no UIKit screens; UIKit only used for `UIImagePickerController`
  wrapper, `EventKit`, PDF rendering via `UIGraphicsPDFRenderer`).
- **Pattern**: Not classic MVVM per-screen. Instead: **one shared `@Observable` data/service
  layer** (`RosterRepository`, `AuthViewModel`, `AppRouter`) injected via SwiftUI
  `.environment()`, consumed directly by views (`@Environment(RosterRepository.self)`).
  Views hold local `@State` for UI-only concerns (sheets, form fields) and call repository
  methods directly — essentially "MV" (Model-View) rather than one-VM-per-view MVVM. Only two
  formal ViewModel types exist: `Rosterra/ViewModels/AuthViewModel.swift`,
  `Rosterra/ViewModels/AppRouter.swift`.
- **Navigation**: Each tab root is its own `NavigationStack`. Root-level routing is a **pure,
  unit-tested function** `AppRoute.determine(...)` (`App/AppRoute.swift`) evaluated in
  `RootView` (`App/RootView.swift`) — gate order: `setup → restoring → login → profileLoading
  → forcedPasswordChange → profileCompletion → deviceAuthGate → managerMain/staffMain`. Sheets
  use a single `.sheet(item:)` bound to one `Identifiable` enum per view (explicit project
  convention documented in `docs/agents.md`: "One sheet per view" — multiple `.sheet`
  modifiers on the same view is banned because SwiftUI presents them unreliably).
- **Dependency injection**: SwiftUI `.environment()` injection of `RosterRepository`,
  `AuthViewModel`, `AppRouter`, `TitlePillCollapse` from `RosterraApp.swift`. Services
  (`AuthService`, `WorkerAPIClient`, `NotificationService`, `DeviceAuthService`, etc.) are
  singletons (`.shared`) rather than injected — a simpler, less testable DI style than formal
  protocol-based injection.
- **Minimum iOS version**: iOS 17.0 (`project.yml` → `deploymentTarget.iOS: "17.0"`).
  Targets iPhone + iPad + **Mac Catalyst** (`SUPPORTS_MACCATALYST: YES`,
  `TARGETED_DEVICE_FAMILY: "1,2"`). Adopts iOS/iPadOS/macOS 26 "Liquid Glass" via
  `#if compiler(>=6.2)` + `if #available(iOS 26.0, *)` availability gating with
  `.ultraThinMaterial` fallback on 17–25 (helpers in `DesignSystem/Theme.swift`:
  `glassSurface`, `glassCapsule`, `glassProminentSurface`).
- **Language**: Swift 5.0 (`SWIFT_VERSION: "5.0"` in `project.yml`), `@Observable`/
  `Observation` framework (not Combine `ObservableObject`, except `AddressSearchCompleter`
  which is a legacy `ObservableObject`/`@Published`).
- **Build system**: Xcode project generated by **XcodeGen** from `project.yml` (explicit file
  refs in `project.pbxproj` — no filesystem sync, so new files require `xcodegen generate`).
  CI: `.github/workflows/ios-ci.yml`. `ci_scripts/ci_post_clone.sh` for Xcode Cloud.
- **SPM dependency**: exactly one package — `firebase-ios-sdk` (`https://github.com/firebase/
  firebase-ios-sdk.git`, `minVersion 11.0.0`, `maxVersion 13.0.0`), with five products used:
  `FirebaseAuth`, `FirebaseFirestore`, `FirebaseStorage`, `FirebaseCrashlytics`,
  `FirebaseMessaging`. **No other third-party dependencies** (no Alamofire, no Kingfisher, no
  analytics SDKs — `URLSession` used directly for the Worker API). Firebase Analytics is
  explicitly NOT used on iOS (only on the web app, per `docs/APP_STORE_SUBMISSION.md`).
- **Backend split**:
  - **Firebase Firestore** — primary datastore, real-time `onSnapshot` listeners throughout,
    **offline persistence enabled** with unlimited cache size
    (`Services/FirebaseBootstrap.swift`: `PersistentCacheSettings(sizeBytes:
    FirestoreCacheSizeUnlimited)`).
  - **Firebase Auth** — email/password only (see §2).
  - **Firebase Storage** — task proof photos (`task_photos/{uid}/...`) and task reference
    photos (`task_ref_photos/...`).
  - **Firebase Crashlytics** — crash reporting (symbol upload wired as an Xcode
    `postCompileScripts` step, Release config only).
  - **Firebase Cloud Messaging (FCM)** — push notification token exchange; APNs token handed
    to FCM which issues the actual push token.
  - **Cloudflare Worker** (`https://sura-roster.com`, `Services/WorkerAPIClient.swift`) — a
    thin authenticated REST layer for operations that need server trust: save availability
    (enforces week locks), create staff Auth accounts, complete forced password change,
    account-deletion request/approve/decline/cancel, and all push-notification triggers
    (`POST /api/send-notification`). Every call sends `Authorization: Bearer <Firebase ID
    token>`.

## 2. Authentication & session model

- **Sign-in only** — email + password (`Services/AuthService.swift` wraps `FirebaseAuth`).
  **No public sign-up.** Staff accounts are created exclusively by a manager
  (`RosterRepository.createStaff` → `WorkerAPIClient.createAuthUser` → Worker
  `POST /api/create-auth-user`, then a Firestore `users/{uid}` doc write + a `CREATE_USER`
  `auditLogs` entry). This is an **invite-only, single-tenant, single-business** app (see
  `docs/BRANDING.md`) — there is no organization signup/join flow and no multi-tenant
  `businessId` field anywhere in the model or rules (explicitly deferred to a future SaaS
  phase; documented as a deliberate non-feature in `docs/agents.md`).
- **Login flow** (`Features/Auth/LoginView.swift`, 576 lines): email/password fields with a
  "flat card + hairline border → brand focus ring" field chrome; on submit
  `AuthViewModel.login(email:password:)`:
  1. `AuthService.signIn` (Firebase Auth).
  2. Fetches `users/{uid}` and validates `status` — rejects `locked`/`inactive` accounts with
     a typed error and force-signs-out (`AuthError.accountLocked` / `.accountInactive`).
  3. Sets `deviceAuthVerified = true` for the session (fresh manual login skips the biometric
     gate for that session) and stashes the **plaintext password in memory**
     (`AuthViewModel.temporaryPassword`) purely so the Account tab can enable Face ID without
     re-prompting — cleared on backgrounding/logout/Face-ID-enable.
  4. Writes `lastLoginAt` (ISO string) to the user doc.
  5. Records `roster_last_manual_login_date` in `UserDefaults` (see 7-day rule below).
  - **Forgot password**: `Features/Auth/LoginView.swift` → `ForgotPasswordSheet` → Firebase
    `sendPasswordReset(withEmail:)` (Firebase hosts the reset page; no custom backend).
  - Login screen shake-animates on error, gated behind `accessibilityReduceMotion`.
- **Roles**: exactly two — `staff` / `manager` (`Models/Enums.swift` → `UserRole`). Role is
  read from `users/{uid}.role` after login; `RootView` branches to `ManagerMainView` vs
  `MainTabView`. **No org-admin/superadmin role yet** — the signed-in manager IS the business
  owner for this single-tenant build (see §15).
- **"Invite" model**: there is no invitation link/token flow. A manager creates the account
  directly with a manager-set temporary password (`mustChangePassword: true` on creation), and
  the staff member is forced through `ChangePasswordView(isForced: true)` on first login
  (`AppRoute.forcedPasswordChange`).
- **Biometric auth (Face ID / Touch ID)** — **two independent layers**:
  1. **Device-auth app-lock gate** (`Services/DeviceAuthService.swift`,
     `Features/Auth/DeviceAuthGateView.swift`): a *local, not server-verified* re-auth gate on
     top of an already-persisted Firebase session. Uses `LAContext.evaluatePolicy(
     .deviceOwnerAuthentication)` (Face ID/Touch ID **with device-passcode fallback**).
     Enablement flag stored per-uid in the Keychain (`roster_device_auth_{uid}`, accessible
     `AfterFirstUnlockThisDeviceOnly`). Re-required after **≥2 minutes backgrounded**
     (`AppConfig.deviceAuthBackgroundRelock = 120s`), enforced in
     `AuthViewModel.handleScenePhase`. Applies to **both roles** — this was a fixed bug
     (`AppRouteTests.testManagerDeviceAuthGate_milestone3Fix`) where managers used to bypass
     it.
  2. **Biometric quick-login credential store** (`Services/BiometricCredentialStore.swift`):
     stores the actual email+password behind a `kSecClassGenericPassword` Keychain item
     protected by `SecAccessControl` with `.biometryCurrentSet` (auto-invalidates if enrolled
     biometrics change), `WhenUnlockedThisDeviceOnly` (never iCloud-synced). Lets the login
     screen offer "Continue with Face ID" without prompting for the password again. **7-day
     staleness rule**: quick sign-in (Face ID or passkey) is refused if the last *manual*
     password login was more than 7 days ago (`roster_last_manual_login_date` in
     `UserDefaults`, checked in `LoginView`).
- **Passkeys** (`Services/PasskeyManager.swift`, `PasskeyStore`): full Apple
  `ASAuthorizationPlatformPublicKeyCredentialProvider` registration/assertion plumbing exists,
  used purely as a **local presence gate** (no WebAuthn relying-party server — a successful
  assertion just unlocks a Keychain-stored Firebase password, same pattern as biometric quick
  login but with an extra passkey ceremony). Associated Domains entitlement
  (`webcredentials:sura-roster.com`) and `apple-app-site-association` are live, but **no UI
  screen calls `PasskeyManager.register()`** — this is dead code with no entry point
  (explicitly noted as an open decision in `docs/ROADMAP-PROGRESS.md`: "keep passkeys...or
  remove?"). Android parity: **not required** (iOS-only half-built feature, no PWA
  equivalent).
- **Session persistence**: handled automatically by the Firebase iOS SDK via Keychain
  (`keychain-access-groups` entitlement required for Mac Catalyst). No manual token
  management. `AuthService.addStateListener` drives `AuthViewModel.handleAuthState`.
- **Multi-tenant/org model**: **none** — single Firebase project = single business. No
  `businessId`/tenant partition anywhere. Confirmed explicitly in `docs/agents.md` §"Tenancy
  (deliberate)".
- **Account-level force sign-out**: `RootView` watches `repo.currentUser?.status` and force
  signs out with a message if it becomes `.locked` or `.inactive` mid-session (e.g. a manager
  locks the account while the staff member is using the app).
- **Password rules** (`Models/BusinessRules.swift` — must be ported exactly):
  - Required: **≥8 characters, ≥1 uppercase letter, ≥1 digit**.
  - Recommended (shown in UI checklist, not enforced): 1 symbol.
  - `BusinessRules.passwordErrors(_:)` returns the list of unmet *required* rules (empty =
    valid); `BusinessRules.passwordRules(_:)` returns all 4 rules with met/required flags for
    a checklist UI.

## 3. Data model — every model + Firestore collection mapping

All models live in `Rosterra/Models/`. Parsing goes through `Models/FirestoreValue.swift`'s
`FS` enum — a tolerant coercion helper (`FS.string`, `.bool`, `.int`, `.double`, `.date`
[accepts Firestore `Timestamp`, `Date`, or ISO-8601 `String`], `.isoString`, `.stringMap`) used
by every model initializer instead of force-casting. **Android must replicate this tolerant
parsing** — several fields are stored inconsistently as Timestamp vs ISO string across the
web/iOS/Worker code paths.

**Firestore collections NOT modeled as Swift structs but referenced**: `auditLogs` (write-only,
best-effort, used for `CREATE_USER` and payroll audit entries), `settings/locations`,
`settings/availabilityLocks` (`weeks` map of weekStartKey→true), `users/{uid}/notificationTokens`
subcollection (FCM tokens: `token`, `platform` [`"ios-native"`], `userAgent`, `enabled`,
timestamps — schema must exactly match `isValidNotificationTokenData` in the deployed rules,
extra keys rejected). Rules also define `masterSheets` and `importBatches` which are
**web/Worker-only** — the iOS app never touches them.

**Firestore listener/query patterns to replicate on Android** (all in
`Services/RosterRepository.swift`):
- Shift window: **28 days back, 56 days forward** from "now" for the staff shifts listener,
  daily_job_assignments, and shift_attendance (both roles use this window for the
  windowed collections).
- Staff timesheets: 5-year lookback, client-side filtered (`submittedAt >= cutoff`).
- Manager timesheets: server-side query `submittedAt >= now - 90 days`
  (`managerTimesheetWindowDaysBack`).
- Manager payslips: `periodStart >= now - 26 weeks` (server-side string range query — dates
  sort lexicographically).
- Staff payslips are **never streamed** — fetched one month ("yyyy-MM") at a time via
  `staffPayslips(monthKey:)`: session memory cache → Firestore's on-disk persistent cache
  (`source: .cache`, zero reads, offline-capable) → server (only for never-downloaded months,
  the current month once per session, or explicit pull-to-refresh). Doc-id bounds ride the
  `{periodStart}_` lexicographic prefix — **no composite index needed**. "Downloaded months"
  tracked per-uid in `UserDefaults` so empty months don't re-hit the server.
- Messages: last 30 days (`sentAt >= now-30d`).
- Tasks: all `active == true` (no date window — shared by both roles).
- Task completions: date range `-28…+56` (both roles, no staffId filter — all staff see
  all completions in the window, used e.g. for "who completed this task").

## 4. Staff screens (full detail)

Tab bar: `Features/Shell/MainTabView.swift` — 5 tabs (`AppRouter.Tab`: home, roster, tasks,
availability, account). **History is not a tab** — pushed from Roster via a "View Shift
History" card; deep links to `history`/`roster` paths route to the Roster tab.

1. **Home** (`Features/Home/HomeView.swift`) — greeting header (time-of-day-aware "Good
   morning/afternoon/evening {firstName}"), company name pill (top-left toolbar,
   `ScreenTitlePill`/`ToolbarLeadingTitlePill`), bell icon with combined badge (unread
   messages + pending daily jobs, capped display at "9"), "Today" section (hero-variant
   `ShiftCard` + inline `ClockInCard` if the shift is clockable), "Approved hours" 2×2
   `StatTile` grid (week/month/year/all-time via `HoursMetrics`), "Upcoming" section (next 3
   published shifts, compact cards, "View roster" link). Pull-to-refresh calls
   `repo.refreshFromServer()`. Context menu on every card: "Add to Calendar" →
   `CalendarService.addShift`. Sheet: `NotificationsSheet` (messages list + Daily Jobs
   panel).
2. **Roster** (`Features/Roster/RosterView.swift`, 416 lines) — `WeekSelector` week strip
   (Monday–Sunday), day-by-day `ShiftCard` list, "Action needed" carousel at top (shifts
   needing submission/resubmission), locked-week indicator for weeks outside the editable
   window. Swipe actions context-dependent: Submit Hours / Report Absence / Undo Absence /
   Edit (label changes based on timesheet state — "Submit hours" vs "Update hours" vs
   "Resubmit hours"). Deep-link handling (`.task(id: router.pendingSubmitShiftId)`) and the
   `SubmitHoursSheet`/`ReportAbsenceSheet` presentations are attached to the `NavigationStack`
   itself (not root content) — a documented gotcha (a pushed `HistoryView` marks the root
   "disappeared" in SwiftUI, so tasks/sheets on it silently stop firing).
3. **Tasks** (`Features/Tasks/TasksView.swift`, 675 lines — largest staff feature file) —
   today's applicable tasks filtered by frequency/assignment, priority badges, due-time,
   photo-required indicator. Complete via in-app camera **only** (never gallery — see
   `CameraPicker.swift`), up to 4 photos, optional note. `TaskCompletionDetailSheet` (full
   detail + photo gallery), `TaskPhotoView` (staff mode never re-hits Firebase; shows sandbox
   cache or "Photo submitted" placeholder), `FullscreenImageView` (pinch-zoom photo viewer).
   Week-strip dots marking days with this user's tasks.
4. **Availability** (`Features/Availability/AvailabilityView.swift`, 335 lines) — week-based
   7-day grid, navigable −2…+12 weeks from current (`BusinessRules.availabilityMinWeekOffset`
   /`MaxWeekOffset`). Tapping a day opens `DayEditSheet` (bottom sheet: Available toggle → All
   day toggle → From/Until time pickers if not all-day). Save writes via
   `WorkerAPIClient.saveAvailability` (goes through the Worker so week locks are
   server-enforced, not just client-side). Locked weeks (past/current always; future weeks the
   manager explicitly locked via "Publish & Lock") show a read-only "Locked by your manager"
   banner — recurring saves/resets skip locked weeks.
5. **History** (`Features/History/HistoryView.swift`, 309 lines, pushed from Roster) — all
   past timesheets grouped by month (`RosterFormat.monthYear`), filter by status (all/pending/
   approved/rejected/absent) and time period, search by location/notes. `TimesheetRow` shows
   rostered vs actual hours, break, manager notes, status pill.
6. **Account** (`Features/Account/AccountView.swift`, 775 lines) — profile photo (native
   `UIImagePickerController` with `allowsEditing: true` square-crop, stored **locally only**
   as `profile_photo.jpg` in the app sandbox — **not uploaded to Firebase Storage/Firestore**,
   so it does not sync across devices), email (with verification badge + pencil→
   `ChangeEmailView`), employee ID (manager-assigned, read-only), member-since, mini-stat row
   (approved hrs / timesheets count / pending count), **Payslips** nav link (→
   `PayslipsView`), Notifications section (alerts-allowed status, pending local-reminder count
   + next-reminder summary, "Enable shift & hours reminders" CTA, "System notification
   settings" deep link), Appearance (Dark Mode toggle — `preferredColorScheme` AppStorage,
   system/light/dark), Security (Face ID/Touch ID toggle via `VerifyPasswordSheet` re-auth
   flow, Change Password), About (App version → `AppVersionHistoryView`, Privacy Policy,
   Terms of Service, Contact Support mailto), **Delete account** section (request/status
   display — see §15), Sign Out. `emailRequestSection` banner appears when a manager has
   flagged `emailChangeRequired`.
   - `PayslipsView` (`Features/Account/PayslipsView.swift`, 317 lines) — floating glassmorphic
     month-picker pill (spring-animated year-wheel + month-grid dropdown, no sheet/chevrons),
     cache-first month loading (see §3), grouped payslip history rows, PDF view/share/print/
     save via `PayslipPDFService` + `ShareSheet`.

**Native UI patterns used throughout staff screens**: `NavigationStack` per tab,
`.sheet(item:)` single-sheet pattern, `.refreshable` pull-to-refresh, swipe actions
(`.swipeActions`), `.confirmationDialog` for destructive/multi-choice actions,
`.presentationDetents([.medium/.large])` + `.presentationDragIndicator(.visible)` for all
sheets, `TimelineView(.periodic(...))` for live-updating clock-session timers and countdown

merge card content into one VoiceOver stop, haptics on nearly every state change

## 6. Roster / scheduling — staff & manager perspective

**Shift lifecycle** (`ManagerShiftStatus` in `Models/Enums.swift`, computed by
`BusinessRules.managerShiftStatus`): `scheduled → inProgress → pendingSubmission →
awaitingApproval → approved` (or `rejected` / `absence` branch). A verified-attendance record
(server clock-in/out) takes precedence over the plain schedule clock for "in progress" vs
"pending submission" determination — an early clock-out means the shift is over even if the
rostered end hasn't passed.

**Staff-visible status** (`StaffShiftDisplayStatus`): scheduled, awaiting_submission, draft,
pending, approved, rejected, absent_reported, absent — driven by
`BusinessRules.displayStatus(for:timesheet:at:)`.

**Draft vs Published**: shifts are created as `draft` (invisible to staff), then
`publishAllDrafts`/`publishShift` flips `status` and stamps `publishedAt` + backfills
`shiftStartAt`/`submittableAfter` (required by Firestore rules for later staff timesheet
writes). Published shifts are **locked from drag/move/copy** in the manager grid.

**Manager operations** (`RosterRepository.swift`): `saveShift` (create/update, recomputes
`scheduledHours` = `(end−start)/3600 − breakMinutes/60`, resets `startReminder6hSent`/
`30mSent` flags and fires a `shift-changed` push if a *published* shift's start actually
moved), `deleteShift` (cascades to attached timesheets in one atomic batch — was a bug fix),
`publishShift`/`publishAllDrafts` (chunks Firestore batches at 500 ops), `copy last week` (UI
action in `ManagerRosterView`), bulk delete.

**Business-rule constants that must port exactly** (`Models/BusinessRules.swift`):
- Break: 0–90 minutes, step 5.
- Staff shift visibility window: **28 days back, 56 days forward**.
- Manager timesheet listener window: **90 days back**.
- Availability edit window: **−2 to +12 weeks**.
- Week start: **Monday** (ISO 8601), timezone **Australia/Adelaide** hardcoded
  everywhere via `RosterCalendar`.
- `calcWorkedHours`: `(endMins − startMins − breakMinutes) / 60`, rounded to 2 decimals,
  clamped ≥0, midnight-crossing handled by adding 1440 to end if `end < start`.
- Shift end crossing midnight: `shiftEndDateTime` adds a day when `end <= start`.
- `isSubmittable`: `now >= (submittableAfter ?? computed shift end)`.

## 7. Availability & leave/absence management

- **Availability**: `UserAvailability` = 7-day map (`Weekday` Monday-first) of
  `DayAvailability{available, allDay, start?, end?}`, stored per-week under
  `users.weeklyAvailability[weekStartKey]` (also a legacy flat `users.availability` fallback).
  Default day = available all-day 09:00–17:00. Saved via the **Worker API** (not a direct
  Firestore write) so week locks are server-enforced.
- **Week locking**: `settings/availabilityLocks.weeks[weekKey] = true`, set by manager via
  "Publish & Lock Availability" (bundled with the Publish Week action) or toggled from a
  roster-week ⋯ menu. Staff sees a **read-only banner** on locked weeks. Current + all past
  weeks are *always* locked for staff regardless of manager action
  (`BusinessRules.isWeekLockedForStaff`).
- **Absence reporting** (staff-initiated): `ReportAbsenceSheet` → `repo.reportAbsence` creates/
  updates a `timesheets/{shiftId}` doc with `status = absent_reported`, zero hours, optional
  reason. Gated by `BusinessRules.canReportAbsence` (only before the shift becomes
  submittable, and only if no existing timesheet or the existing one is `rejected`).
  Undoable via `repo.undoAbsenceReport` (hard delete) while still `absent_reported`.
- **Absence confirmation** (manager-initiated, terminal): `repo.confirmAbsence` sets
  `status = absent` (distinct from `absent_reported` — a no-show that was never
  self-reported still needs a manager path to close it out, though the primary manager UI for
  this is via the Timesheets approve/reject flow, not a dedicated "mark absent" button
  currently surfaced in the grepped views — verify against `ManagerTimesheetDetailSheet`
  during Android build).
- There is **no formal leave-request/annual-leave/sick-leave type system** — absence is
  binary (worked / didn't attend), and PTO accrual is not modeled anywhere in this codebase.

## 8. Time & attendance / clock in-out, timesheets

Two parallel systems working together:

1. **`ClockSession`** (device-local only, `UserDefaults`) — the live-timer UX. Persisted per
   uid, survives relaunch mid-shift. **Why local-only**: deployed Firestore rules block staff
   timesheet writes until `submittableAfter` (i.e. after the rostered shift ends), so a
   real-time clock-in can't be written to the "system of record" `timesheets` collection.
   - `startBreak`/`endBreak`/`clockOut` mutate the struct; `workedSeconds`,
     `totalBreakSeconds`, `timesheetBreakMinutes` (rounded to nearest 5, clamped 0–90),
     `paidWorkedSeconds(rosterStart:)` — **paid time starts at the rostered start, not actual
     clock-in**, so an early check-in's pre-shift minutes are excluded; a late check-in's paid
     start is the actual clock-in. Break overlap with the unpaid pre-shift window is
     partially deducted (only the paid-window portion). Fully covered by `ClockSessionTests`
     (see exact test cases below — must reproduce bit-for-bit on Android).
   - `useRosteredEnd` flag: at clock-out, staff choose "Stayed back for extra work" (records
     actual clock-out time, editable in SubmitHoursSheet) vs "Finished at my rostered time"
     (seeds the roster's end time).
2. **`ShiftAttendance`** (Firestore `shift_attendance/{shiftId}`) — the **server-authoritative,
   tamper-resistant audit trail**, written alongside every Start/End Shift tap:
   - `clockInAt`/`clockOutAt` = `FieldValue.serverTimestamp()` (Firestore rules require these
     exact server-time values — a manipulated device clock cannot forge them).
   - `clockInDeviceAt`/`clockOutDeviceAt` = the device's own clock at the same instant, so the
     manager portal can flag a **>2 minute skew** as possible tampering.
   - GPS `Fix` captured at both taps (when-in-use location, `kCLLocationAccuracyNearestTenMeters`,
     accepts a cached fix <30s old). Evaluated against the shift's saved `RosterLocation`
     geofence: `geofence = distance <= (radius + accuracy) ? .inside : .outside`; `.unknown`
     if no workplace coordinates or no GPS fix.
   - **Geofence policy — different rules for start vs end**:
     - *Start*, geofence enforced (`RosterLocation.geofenceEnforced == true`): outside radius =
       **hard blocked** ("You are outside the work zone.").
     - *Start*, not enforced: lenient 250m allowance (`ClockInCard.lenientStartRadius`);
       further out **warns + records but allows** (confirmation dialog).
     - *End*: **never restricted** — best-effort capture only, so staff can end a shift from
       home without prompts.
   - Trust model documented as **deliberately advisory** for the geofence verdict — only the
     server timestamps are hard-trusted; the manager reviews raw coordinates on the "Verified
     Attendance" card.
   - Offline/failure: local session always works; a failed sync shows "recorded on device,
     couldn't sync" — absence of a verified record is itself the signal to the manager.
   - Fires best-effort `shift-started`/`shift-ended` Worker notifications on success.
3. **`SubmitHoursSheet`** (`Features/Shared/SubmitHoursSheet.swift`) is where clock-session
   data actually becomes a `Timesheet`: pre-fills from (priority order) existing timesheet →
   recorded clock session → rostered times; break defaults from the clock session's computed
   break minutes; validates `workedHours > 0`; warns (dismissible) if there are uncompleted
   tasks for the day before allowing submit. **Editable-until-approved**: a `pending` timesheet
   stays editable (button label reads "Update hours"); only `approved`/`absent` lock it.
4. **Manager correction**: `managerAdjustTimesheet` lets a manager fix a submitted timesheet's
   times without touching the original rostered times or the verified attendance record
   (kept for audit).
5. **Approve/reject workflow**: `approveTimesheet` (stamps `approvedBy`/`approvedAt`, fires
   `timesheet-approved` push), `rejectTimesheet` (stamps `rejectedReason`, resets
   `rejectedAt`/`rejectionReminderCount`, fires `timesheet-rejected` push). Staff sees the
   rejection and can resubmit → status returns to `pending`.

**Timesheet status enum** (`TimesheetStatus`): `draft, pending, approved, rejected,
absent_reported, absent`. **Staff-editable statuses**: `draft, pending, rejected,
absent_reported`. **Locked**: `approved, absent`.

## 9. Payroll (Australian market)

Australian-market specifics throughout (AU TFN, ABN/ACN, AU Superannuation Guarantee, AU
timezone) confirm this is an **AU-only** product; Android build should assume the same market
unless told otherwise.

- **`TFN` validation** (`Models/TFN.swift`) — the exact algorithm to replicate: normalize to
  digits, must be exactly 9 digits, reject all-same-digit numbers (`Set(digits).count == 1`),
  weighted sum with weights `[1,4,3,7,5,8,6,9,10]` positionally, valid iff `sum % 11 == 0`.
  Format as "XXX XXX XXX"; mask as "\*\*\* \*\*\* {last3}"; `last4` helper for payslip
  snapshots. TFN is **manager-entry only**, shown masked, retained even after account deletion
  (ATO record-keeping).
- **Superannuation**: `BusinessRules.defaultSuperRatePercent = 12.0` (AU SG rate since
  2025-07-01, up from 11.25% — comment notes this was a mid-project bump). Per-staff override
  via `AppUser.superRate` or `StaffWageProfile.superRate`; can be fully **disabled per staff**
  (`StaffWageProfile.superEnabled = false`, e.g. under-18 casuals under 30h/week) — a disabled
  profile generates payslips with 0% super and the PDF omits the super block entirely.
- **Wage structure** (Xero-Payroll-AU-modeled, `Models/WageModels.swift`): `WageAward`
  (modern-award-style: name, code, industry, legacy embedded `classifications`) →
  `EarningsLine` (the modern replacement — a `kind: "earningsLine"` doc can itself BE a
  classification level via `isClassificationLevel`, carrying `baseHourlyRate` (Mon–Fri) +
  `weekendHourlyRate` (Sat/Sun/PH); default weekend/PH multipliers of **1.5×** and **2.25×**
  base apply when no explicit weekend rate is set (`buildDraftPayslip`), overtime defaults to
  **1.5×** base) → `StaffWageProfile` (per-staff assignment: award + classificationLevel +
  earningsLineIds[] + optional `hourlyRateOverride` + `employmentType` + `ageGroup` +
  `effectiveDate` + `superEnabled`/`superRate` + `active`). Rate resolution precedence
  (`resolvedHourlyRate`, unit-tested exhaustively): explicit override → matching
  classification-level earnings line → legacy award-embedded classification → any assigned
  fixed/per-unit ordinary-hours line. **Never silently pays $0** — a resolution failure must
  surface to the manager (this was a real production bug, fixed and covered by
  `PayrollTests.testResolvedHourlyRateFromOrdinaryEarningsLine`).
- **Payslip lifecycle** (`payslips` collection, `Payslip` struct): **draft → under_review →
  approved → submitted → (archived)**. Staff visibility (`PayslipStatus.isStaffVisible`) is
  **only** `submitted`/`archived` — enforced by Firestore rules (`firestore.rules.payroll-
  proposed`), not just client filtering. Editable (`isEditable`) only in `draft`/
  `under_review`.
  - **Auto-generation**: idempotent, client-side "stand-in for a server cron" — the *first
    manager session that opens on/after Monday* generates drafts for the **most recently
    completed week** (`RosterRepository.autoGeneratePayrollDraftsIfNeeded`), from approved
    timesheets × active wage profiles. Double-checks the server before creating (guards
    against a stale local cache overwriting a manager's in-progress edits). Manual "Generate"
    button also available per period.
  - **Snapshot semantics**: generation copies staff name/award/classification/resolved rate
    **onto** the payslip permanently — later wage-profile/award/roster edits never retroactively
    change an issued payslip. A manager must explicitly hit "Regenerate" (draft/under_review
    only) to recompute.
  - **Money math** (`PayrollCalculator.totals`, exactly unit-tested — port formula verbatim):
    - `ordinaryAmount = round2(ordinaryHours × baseHourlyRate)`, same pattern for
      weekend/publicHoliday/overtime amounts.
    - `extrasAmount = round2(sum of extraEarnings.amount)`.
    - `gross = round2(ordinary + weekend + publicHoliday + overtime + extras)`.
    - **Super base (OTE) excludes overtime** and excludes any earnings line flagged
      `exemptFromSuper`: `superAmount = round2((ordinary+weekend+publicHoliday+non-exempt
      extras) × superRate/100)`.
    - `deductions = round2(otherDeductions + salarySacrifice)`.
    - `net = round2(gross − payg − deductions)`.
    - `round2(x) = (x*100).rounded()/100` (standard half-up rounding via Swift's `.rounded()`).
  - **Hours bucketing** (`PayrollCalculator.hoursBuckets`): splits approved worked hours per
    shift-date into ordinary (Mon–Fri) vs weekend (Sat/Sun) using `RosterCalendar.calendar`'s
    `.weekday` component (1=Sun, 7=Sat in Apple's Gregorian calendar numbering — `weekday == 1
    || weekday == 7` = weekend). Bad/unparseable date keys are silently skipped.
  - **Audit trail**: every generate/edit/status-change/download appends a
    `PayslipAuditEntry` (action, userId, userName, timestamp, detail) to the doc's `audit[]`
    array, plus a best-effort global `auditLogs` entry.
  - **Position** on the payslip = the shift `department` value worked most often in the period
    (mode, by count) — department doubles as a free-text "role" label (e.g. "Console
    Operator").
  - **PDF** (`Services/PayslipPDFService.swift`) — A4 (595.2×841.8pt @72dpi), monochrome
    ink-on-white design (no color fills except the company logo), letter-spaced section labels,
    company block (logo+name+address+ABN), employee/period two-column block, earnings table,
    tax & deductions, superannuation block (omitted entirely if `superRate == 0`), bordered
    net-pay panel, Fair Work Act 2009 footer disclaimer. **Same renderer produces the live
    manager preview AND every export/print/share** — guarantees WYSIWYG.
  - Staff → Account → Payslips shows history grouped, PDF view/share/print/save (`ShareSheet`
    wrapping `UIActivityViewController`).
- **Payroll Gaps** (`BusinessRules.payrollGaps`): flags published, already-ended shifts within
  a period lacking an approved timesheet, with a reason enum (notSubmitted /
  draftNotSubmitted / pendingApproval / rejected / absenceUnconfirmed) — surfaced to the
  manager via `PayrollGapsSheet` before generating drafts, since `generateDraftPayslips`
  silently only counts approved hours.
- **Employee ID**: manager-assigned alphanumeric code (`AppUser.employeeId`), stored
  uppercase, snapshotted onto payslips at generation, shown on staff Account and payslip PDF —
  replaces a previously-used truncated-UID identifier.

## 10. Tasks / Daily Jobs (two entirely separate features)

### Tasks (docs/tasks-feature.md, RosterTaskTests)
- Manager creates one-off/daily/weekly tasks, optionally `assignedTo` specific staff
  (nil/empty = everyone), with `priority` (low/normal/high, sort weight high=0/normal=1/low=2),
  `dueTime`, a per-task choice of photo-proof vs tick-to-complete (`requiresPhoto`, nil legacy
  = true), optional `endDate` to stop a recurring task, optional manager reference photo.
- **Scheduling logic** (`RosterTask.isActive(onDayKey:weekday:)`, exact port needed):
  `active == false` → never active; `endDate` set and `dayKey > endDate` → not active;
  `frequency == "once"` → active only when `date == dayKey`; `"weekly"` → active when
  `dayOfWeek.contains(weekday)` (1=Monday…7=Sunday); default (`"daily"`) → always active.
- **Assignment**: `isAssigned(to:)` — nil/empty `assignedTo` = everyone; otherwise must
  contain the uid. Push-notification recipients (`notificationRecipientIds`) resolve the same
  way, deduped via `Set`. `assigneesChanged` compares normalized assignee sets so **title-only
  edits do not re-notify staff** (only create, or an assignee-list change, fires
  `message-task`).
- Completion doc id = `{taskId}_{date}` — **one completion shared across all assignees for
  that day** (not per-assignee). `completeTask` uploads up to `RosterRepository.
  maxPhotosPerCompletion = 4` photos, each compressed via `ImageCompressor.jpegData`
  (downscale longest edge to 1600px, step JPEG quality 0.7→0.1 in 0.15 steps, last-resort
  half-size@0.1 quality) to fit a **2 MB hard cap**. First photo mirrors into legacy
  `staffPhotoUrl` field for PWA parity; new uploads store `gs://` Storage references (not
  public download-token HTTPS URLs) — manager review reads through Storage rules instead.
- **Photo lifecycle** (Firebase free-tier cost control, `Services/TaskPhotoCache.swift`):
  photos live **only** in the app sandbox, never the phone photo library. Staff local copies
  auto-delete at the **end of the week they were taken** (`removePhotosBeforeCurrentWeek`,
  launch-time sweep) — after that staff see a "Photo submitted" placeholder and staff views
  **never re-download from cloud**. Manager: downloads each photo once
  (`managerDownloadedAt` stamp starts the retention clock), serves subsequently from sandbox,
  keeps a **90-day local review history** (`removePhotosOlderThan(days: 90)`). Cloud cleanup:
  manager's explicit "Reviewed — delete photo from cloud" button, plus a **14-day launch-time
  backstop sweep** (`cleanupExpiredTaskCloudPhotos`) that deletes any Storage object first
  downloaded >14 days ago even if the manager never clicked the button.
- **Redo flow**: manager `requestTaskRedo` deletes the cloud photo(s), sets
  `status: "redo"`, `redoReason`, `reviewedBy/At` — reopens the task for that day on staff's
  side.

### Daily Jobs (docs/daily-jobs-feature.md, DailyJobTests) — completely separate
- Managers keep a **permanent reusable job-template library** (`daily_job_templates`, never
  auto-deleted, deleting a template only removes it from the library — existing shift
  assignments keep their snapshotted title).
- Manager assigns a selection of templates to **one staff member's one specific shift** via
  `DailyJobAssignSheet` (multi-select checkboxes, search, inline "+ Add Job", trailing trash).
  Doc id `{shiftId}_{templateId}` makes re-assignment idempotent; `setDailyJobs` diffs the
  selection (adds new, removes deselected, **preserves completion state** of unchanged ones).
- Staff visibility: `isVisibleToStaff(now:)` = the assignment's `date` (shift date) equals
  today's Adelaide calendar day — **visible for the entire shift date**, not gated by
  rostered end time, and disappears once the date rolls over (manager history persists
  forever). Sort is **title-only, stable across complete/undo** — deliberately does NOT
  reorder on toggle (a row jumping after a tap reads as a failed tap and invites mis-taps).
- Staff completes/undoes via the **Home bell notification panel** (`NotificationsSheet`), not
  the Tasks tab. Bell badge = unread messages **+ pending (incomplete) daily jobs count**.
- "All jobs completed for a shift" fires a `jobs-all-completed` push (computed client-side by
  checking sibling assignments, since the live listener for the just-completed one hasn't
  necessarily echoed back yet).

## 11. Notifications

**Local notifications** (`Services/ShiftReminderScheduler.swift`) — fully device-local, no
Apple entitlement required, still fire after the app is force-quit (iOS delivers them). Exact
reminder slots per shift, all relative to **rostered** (not verified) start/end — port
verbatim:

| Slot tag | Timing | Title | Body |
|---|---|---|---|
| `24h` | 24h before start | "Shift tomorrow" | "You have a shift tomorrow at {start}." |
| `6h` | 6h before start | "Shift today" | "Your shift starts in 6 hours, at {start}." |
| `1h` | 1h before start | "Shift soon" | "Your shift starts in 1 hour, at {start}." |
| `30m` | 30m before start | "Shift in 30 minutes" | "...at {location}." |
| `5m` | 5m before start | "Ready to start?" | "Start Shift is now available." |
| `forgot-start` | 10m **after** start | "Don't forget to start your shift" | cancelled the instant `startShift` succeeds |
| `forgot-end` | 10m **after** rostered end | "Your shift has ended" | only armed while clocked in; cancelled on `endShift` |
| `submit-hours` | 15m after rostered end | "Submit your hours" | only if no filed timesheet; look-back window 48h for past shifts |

`sync(shifts:clockedInShiftId:filedShiftIds:)` is **idempotent** — clears every previously
scheduled `shift-reminder.*` id and rebuilds from the live roster on every shifts/timesheets
listener update. Caps at **8 shifts** (iOS hard-limits 64 pending local notifications; 8×≤8
reminders stays safe). "Filed" statuses (`isHoursFiled`): pending, approved, absent_reported,
absent — draft/rejected/nil are NOT filed (still need reminders). Uses
`UNTimeIntervalNotificationTrigger` keyed to the absolute instant (not a calendar trigger) so
device-timezone changes can't shift the fire time.

**Remote push** (APNs → FCM → Firestore, `Services/NotificationService.swift`,
`AppDelegate.swift`): `Messaging.messaging().apnsToken = deviceToken` on APNs registration;
`MessagingDelegate.didReceiveRegistrationToken` writes the FCM token into
`users/{uid}/notificationTokens/{urlEncodedToken}` (schema: `token, platform: "ios-native",
userAgent, enabled, createdAt/updatedAt`) — **this exact subcollection**, not a flat
`fcmToken` field, is what the Worker's send pipeline reads (a previously-shipped bug had iOS
writing to a field the pipeline never read — silently undeliverable pushes). `aps-environment:
production` entitlement; `UIBackgroundModes: [remote-notification]`. Push is a switch
(`AppConfig.pushEnabled = true`) — gated behind the paid Apple Developer team which was wired
2026-07-15.

**Notification event registry** (hyphenated names, shared with the Worker/PWA —
`docs/reference/worker-notifications.ts`): `roster-published`, `timesheet-submitted`,
`timesheet-approved`, `timesheet-rejected`, `timesheet-absent`, `timesheet-reminder`,
`message-task`, `shift-changed`, `shift-cancelled`, `shift-started`, `shift-ended`,
`job-assigned`, `jobs-all-completed`, `payslip-generated`, `task-completed`,
`shift-start-6h`/`shift-start-30m` (Worker-cron-only). All sent via
`WorkerAPIClient.sendNotification(event:shiftIds:timesheetId:recipientIds:)` →
`POST /api/send-notification` (fire-and-forget, errors swallowed).

**Local-alert backups**: `RosterRepository` also fires **local** notifications as a same-
process-alive backup for two live events even without waiting for push: timesheet
approve/reject decisions (`handleTimesheetDecisionAlerts`, "primed" on first snapshot so login
doesn't spam) and newly-published shifts (`handleRosterPublishedAlerts`). Closed-app delivery
still depends on FCM/APNs.

**Deep-link routing** (`ViewModels/AppRouter.swift.handleNotificationUserInfo`): maps
`event`/`kind`/`slot`/`shiftId`/`url` payload keys to tab + pending-shift-id state:
`timesheet-rejected` → open Submit Hours for that shift; `timesheet-approved`/
`roster-published`/`shift-changed`/`shift-cancelled` → Roster tab; `submit-hours`/`forgot-end`
local slots → open Submit Hours; other `shift-reminder` slots → Home tab; unrecognized →
falls back to a `url` path substring match (`roster`/`history`→Roster, `tasks`/`job`→Tasks,
`availability`→Availability, `account`→Account, `home`→Home). Also handles custom URL scheme
deep links (`?submit=<id>`, `?absent=<id>` query params) via `RosterraApp.onOpenURL`.

**Notification permission UX**: `NotificationService.requestAuthorizationAndRegister()` called
on every login (iOS de-dupes the system prompt). Account tab shows an explainer alert before
the first ask ("Enable shift & hours reminders?"). Foreground delivery triggers a haptic
(`Haptics.Notification.delivered/urgent` — urgent escalation driven by a payload `urgent`

## 13. Offline behavior, caching, background sync

- **Firestore offline persistence**: enabled with **unlimited** on-disk cache size
  (`FirebaseBootstrap.configure()` → `PersistentCacheSettings(sizeBytes:
  FirestoreCacheSizeUnlimited)`). All `onSnapshot` listeners transparently serve cached data
  offline; writes queue and flush on reconnect (standard Firestore SDK behavior — no custom
  offline-queue code was found, i.e. **no bespoke outbox/retry system**; the app relies
  entirely on the Firestore SDK's built-in offline write queue).
  - `docs/smoke-test.md` explicitly calls out testing this: "Airplane mode → previously loaded
    data still renders from cache; writes fail with a visible error (post Milestone 5) rather
    than crashing."
- **Explicit cache-first reads** (bypassing the live-listener pattern) for one feature: staff
  payslips (`staffPayslips(monthKey:)`, see §3/§9) — a deliberate 3-tier cache (session memory
  → `source: .cache` Firestore query → server), because payslips are cold/append-only data
  that doesn't benefit from a permanent live listener the way shifts/timesheets do.
- **Local persistence outside Firestore**:
  - `ClockSession` → `UserDefaults` (per-uid keyed), see §8.
  - Task/profile photos → app-sandbox `Documents` directory (`TaskPhotoCache`,
    `profile_photo.jpg`), never Photos library, with the retention sweeps described in §10.
  - Biometric/passkey credentials → Keychain (see §2).
  - "Last manual login date", "last FCM token", "downloaded payslip months" → `UserDefaults`.
  - Pending local notifications → `UNUserNotificationCenter` (OS-managed).
- **Pull-to-refresh** (`refreshFromServer()`) forces a one-shot `source: .server` re-fetch of
  the role-appropriate queries as a fallback on top of the always-on listeners — mirrors each
  role's exact listener queries so a manager refresh doesn't accidentally run staff-shaped
  queries (a documented past bug).
- **No background sync / BGTaskScheduler** — see §12. All sync is either live-listener-driven
  (while foregrounded) or push-triggered.
- **`pendingFirstSnapshot`** gating in `RosterRepository.start(uid:)`: `isLoading` stays `true`
  until every listener relevant to the resolved role has delivered its *first* snapshot
  (users, tasks, task_completions, shifts, timesheets) — prevents a "flash of empty roster"
  before role-specific data streams in (a fixed perf/UX bug, M8 in the roadmap).

## 16. Other notable business rules & edge cases

- **`RosterCalendar`/`RosterFormat`** — the single source of truth for ALL date/time logic;
  timezone `Australia/Adelaide` and Monday-first weeks are hardcoded module-wide (not
  user-configurable). `Calendar` is cached as a `static let` (was previously rebuilt on every
  call — a real perf bug, fixed in Milestone 8). Every date operation across the app — shift
  windows, week keys, submittable-after gates, payslip period bounds — MUST route through
  this to stay consistent; Android needs an equivalent single calendar utility pinned to the
  same timezone/week-start.
- **DST correctness**: `BusinessRulesTests.testShiftInstantsAcrossDSTStart` explicitly proves
  shift start/end instants are **wall-clock anchored**, not offset-anchored, across Adelaide's
  DST transition (2026-04-05) — an 8-hour wall-clock shift spanning the "fall back" is 9 real
  hours. Must replicate on Android (`ZonedDateTime`/`java.time` with the IANA
  `Australia/Adelaide` zone handles this correctly if done right, but it's an easy thing to
  get wrong with naive `Instant` math).
- **Timesheet doc-id-equals-shift-id convention**: staff-created timesheets always use the
  shift's own id as the timesheet doc id (1:1 relationship) — this simplifies lookups
  (`repo.timesheet(forShift:)`) but means a manager-side "multiple timesheets per shift"
  scenario is structurally impossible.
- **O(1) index maintenance pattern**: `RosterRepository` maintains `shiftsById`,
  `timesheetsByShiftId`, `usersById`, `attendanceByShiftId` dictionaries via Swift property
  `didSet` observers whenever the backing arrays are reassigned by a listener — converts what
  were O(n) or O(n²) list-view lookups into O(1). A real, documented performance fix (Milestone
  8) worth replicating in an Android ViewModel/repository layer (e.g. via `Map` indices kept in
  sync with `StateFlow` updates).
- **Best-effort vs. must-succeed writes**: the codebase distinguishes writes that MUST surface
  errors (timesheet submit, shift save) from ones that are explicitly best-effort/fire-and-
  forget but still logged on failure (`RosterRepository.bestEffort(_:_:)` wraps push
  notifications, audit-log writes, photo-download-timestamp stamps) — never silently
  swallowed, always logged via `OSLog`/`Logger`, never blocks the primary user action.
  Android should adopt the same two-tier error-handling discipline.
- **Firestore rules enforce server-side what the client can't be trusted to**: staff can never
  write timesheet approval fields, `shift_attendance` clock times must equal
  `request.time` (server timestamp) or the write is rejected outright, `wages` collection is
  entirely unreadable by staff, absence self-reports must carry zero hours. **These rules are
  the actual security boundary** — the iOS client's role-based UI gating is a convenience
  layer on top, not the enforcement mechanism. Android's client-side logic can mirror the UI
  gating, but real security parity requires nothing more than talking to the same Firestore
  rules (no separate backend work needed for Android specifically).
- **Composite-index awareness**: several query designs are explicitly shaped around what
  Firestore composite indexes are actually deployed (`docs/reference/firestore.indexes.json`)
  — e.g. `publishAllDrafts` deliberately queries by `date` only and filters `status == draft`
  **client-side** rather than adding a `(status, date)` composite query, because that index
  isn't deployed (documented FAILED_PRECONDITION production bug). Any new Android query
  against the same Firestore project must check this same indexes file before assuming a
  compound `.where().where()` query will succeed.
- **Notification token schema is strict**: extra/missing keys in a `notificationTokens` doc
  are rejected by `isValidNotificationTokenData` in the deployed rules — Android's FCM token
  write must match the schema exactly (`token, platform, userAgent, enabled,
  createdAt/updatedAt`), with `platform` presumably needing a new whitelisted value (iOS uses
  `"ios-native"`) — **check the deployed rules for an Android-equivalent platform string
  before shipping push on Android**, or tokens will be silently undeliverable exactly like the
  documented iOS bug.
- **Single-tenant assumption pervades the data model**: no `businessId` field anywhere,
  Firestore rules are role-based (`isManager()`) not tenant-scoped. An Android app for this
  same backend inherits this limitation automatically — do not invent tenant scoping
  client-side without a corresponding rules change.
